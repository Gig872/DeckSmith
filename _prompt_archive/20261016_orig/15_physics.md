# 15 物理可行性（地基级约束：跑得通 ≠ 讲得通）

**核心**：一个"能跑但物理上荒谬"的模型，价值为零。**每次交付前必须保证物理自洽**，
并能用自然语言讲清"这个模型在物理上为什么成立"（故事性），而不是只罗列卡片。

## 一、动手前：先写物理意图（`set_model_intent`）
建卡前**必须**先想清并记录四项；**写不出自洽的意图，说明还没想清楚——不许动手建卡**：
1. **场景**：这是什么系统？什么工质（水/蒸汽/气）？开式还是闭式？
2. **驱动**：靠什么让流体动起来（压差 / 泵 / 重力 / 给定流量）？
3. **能量**：能量从哪来、到哪去？有没有加热/做功/排热？**是否平衡**？
4. **预判范围**：预期压力 / 温度 / 流量的大致量级是多少？

## 二、边界条件自洽（最容易出错的地方）
- **质量必须能平衡**：稳态要求"进 = 出"。若一端**给定流量注入**，另一端必须能让质量**排出去**
  （定压边界/出口），否则质量会不断积累 → RELAP5 报 **mass error 暴涨**。
- **不要对同一端既定压力又定流量**（过约束）。
- 定压/定温边界（tmdpvol）适合"大容量源/汇"；定流量边界（tmdpjun）适合"泵/注入"。
- **封闭端 + 有加热** = 温度必然单调上升（能量没有出路）——除非这是你**有意**模拟的蓄热过程。
- 面积突变时，接管面积 ≤ 相邻控制体最小面积。

## 三、量级常识（水/蒸汽，SI）
- 压力：常见 0.1–15 MPa；**压力必须 > 0**。
- 温度：常温水 ~300 K；1 MPa 饱和温度 ~453 K；压水堆 ~560–600 K。
  明显高于/低于这些范围（如 >900 K 或 <250 K）要**先怀疑读错表，再查设计**。
- 温度 ≤ 饱和温度则为过冷液；空泡份额 0=纯液、1=纯汽。

## 四、跑完后：必须校验（`check_sanity`），并回头核对
1. `check_sanity(o_path)`：看压力/温度极值、**质量守恒误差**是否过关。
2. 与第一步写下的**预判范围**逐一比对——**不一致就必须回头改设计**（边界/几何/时长），
   **不得**把不合理结果解释成"被加热了/大概是这样"就交付。
3. 交付时必须用自然语言讲清物理：*"谁驱动、能量如何平衡、为什么这个结果是合理的"*。

> 记住：你的职责是**导师/翻译器**，不是码字工。讲不出物理故事的模型，等于没做。

## 五、框架只给"够用"的体检，精细判据靠你自己学（重要）
框架预置的物理校验**到此为止**，只有三道**通用**硬伤体检：
1. **系统守恒**（`check_sanity`：质量误差 + 压力/温度量级）；
2. **拓扑连接**（`result_summary`：重复连接）；
3. **节点守恒**（`result_summary`：每个控制体 进=出）。

**更精细、更专业的物理判据（特定瞬态稳定性、特殊部件行为、经验限值…）不在框架里硬编**——
那样会变成无穷无尽的补丁群。遇到这类问题，**你自己现学现用**：
- **先 `lookup_doc` 查本地手册**（对 RELAP5 卡格式是**权威**，且一次会给全该部件整组小节）；
- 手册不够/太含糊（如某部件的物理行为、经验取值），再 `web_search`（用**简短关键词**，
  别把一整串数字/卡号堆进去）→ 看**摘要**挑最相关的链接 → 用 **`web_fetch` 抓正文**深读；
- 想清楚后落到模型上，跑通且物理自洽后，把结论用 `remember` / `save_example` **沉淀**，
  下次遇到直接复用。**越用越强，而不是等框架加补丁。**
